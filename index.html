Payment Investigation Toolkit

Operations dashboard & investigation suite · v1

12
Dashboard panels
6
Grafana dashboards
4
Audiences served
1
Shared data pipeline

Overview

A day-to-day investigation tool covering terminal health, bank settlement, transaction performance and support tickets across a payment terminal fleet, paired with a companion Grafana layer for real-time alerting. A scheduled Python pipeline logs into the acquiring bank's portal, scrapes and merges settlement exports, runs reconciliation, and writes the result into a shared database so the dashboard and Grafana always agree.

Stack

Python Playwright MariaDB Chart.js SheetJS Grafana

Reconciliation engine

A 14-strategy waterfall matching engine reconciles the acquirer's settlement export against bank markoff files, resolving every transaction to a Strong Match, Partial Match, or Unmatched using identifiers like transaction ID, RRN, amount, TID, MID and card BIN/last-4 — amount and date alone is never treated as sufficient, so at least one hard identifier has to line up before a match is accepted.

Panels covered

Dashboard Batching Settlement Diagnostics Recon Transactions Tickets Terminals Registry All Sites Alerts Settings

Built for four jobs, one tool

  • Frontline support / NOC — is this site or terminal down right now, and what should be logged.
  • Reconciliation / finance — did the bank settle correctly, and what's still outstanding.
  • Ops manager — a fleet-wide scan for what's trending wrong across all sites.
  • Engineer / pipeline operator — is the data pipeline healthy, and is an issue a device fault or a data fault.

What it replaced

  • Manual cross-checks against the bank's settlement export → automatic transaction and amount-difference flags on every batch.
  • Eyeballing timestamps to guess which terminals were settling late → automatic Daily / Irregular / Force-Batch classification.
  • Decline-code knowledge living in one or two people's heads → five named, numbered response playbooks with clear trigger conditions.
  • Checking two separate support desks with no shared view → a unified ticket view that flags sites open in both systems at once.

Companion layer

Six Grafana dashboards (fleet overview, per-terminal drill-down, settlement, alerts & thresholds, pilot-site comparison, and pipeline health) sit alongside the custom dashboard, reading the same database for continuous, real-time refresh and alert-rule configuration. A rule watching for the pipeline itself going quiet for over 13 hours catches a broken pipeline before anyone notices stale data.

What's next

A React + Tailwind rebuild of the terminal management view is separately specced, aimed at replacing the current single-file HTML dashboard with a proper componentised frontend.

BallChecker

Overview

A mobile-first PWA that analyses South Africa's six national lottery games — scoring balls, generating ensemble predictions, and surfacing heatmaps and draw history. It ships alongside BEP, a private, embedded engineering platform used to run the product's own development lifecycle, in a single Next.js app to share components and avoid a second build pipeline.

Stack

Next.js / React 19 TypeScript Tailwind v4 Flask + SQLite Recharts Vercel + Fly.io Grafana PostHog

Analytics engine

Each ball is scored across 9 dimensions — frequency, gap, recency, pair, pattern, momentum, overdue, ensemble and composite — rolled into a 1–5 star verdict, alongside HOT / OVERDUE / COLD / NORMAL status tags and 4 AI pick strategies (Ensemble Primary, Frequency Bias, Gap Balanced, Hot Momentum). An auto-fetcher scrapes the official lottery site twice weekly and 8 analytics engines process the results into the API the frontend consumes.

BEP — the self-built engineering platform

A lightweight GitHub + Linear + Azure DevOps hybrid, covering planning, build & test, deployment (an 8-stage pipeline with approval gates), release and ops — including live DORA metrics computed client-side. Runs entirely on localStorage with no backend, using a custom DOM event for cross-tab reactivity, and keeps an append-only audit trail that survives deletion of the underlying record.

Overview

A real-time market data platform ingesting live crypto, stock and financial-news feeds around the clock, publishing everything through a shared mapping/validation pipeline into one MySQL-backed store — with a per-feed Grafana dashboard and a plain-language Insights panel sitting on top of the same data.

Stack

Flask + gunicorn Fly.io Machines MySQL Grafana Binance WS Finnhub Alpha Vantage

Three feeds, one pipeline

Crypto trades stream continuously from Binance's WebSocket API, stock trades pull from Finnhub during market hours, and Alpha Vantage news is polled hourly and scored for sentiment — all three land through the same ingest → map → validate → publish pipeline and the same admin tooling, rather than three one-off scripts.

Insights panel

Four standing questions — what to watch in crypto, which stock is trending, the market mood from recent news, whether markets are moving together — answered live from whatever's actually been ingested, and explicitly labelled informational rather than investment advice.

Field note — routing around a 451

The crypto worker got a straight HTTP 451 from Binance when running out of Fly's Johannesburg region — confirmed by probing from other regions — so it runs from Amsterdam while the rest of the app, including the other two feeds, stays in Johannesburg.

Admin control, with a hard guardrail

An admin panel can start, stop and restart the streaming workers directly through the Fly Machines API — with a hardcoded denylist that refuses to touch the web process group no matter what calls it, so a bug or a crafted request further up the stack can't take the app down through that path.

Grafana Monitoring

Four dashboards — one per feed plus a pipeline overview — all reading from the same MySQL store for continuous refresh.

Crypto Stream — three independently-scaled price panels, volume, momentum and volatility
News Stream — sentiment breakdown and top mentioned tickers
Pipeline overview — files ingested, rows published, exceptions
Stocks Stream — Finnhub trade volume and recent trades

Known issues

MediumThe MySQL host was OOM-killed 8 times in 17 hours before root-causing it to mysqld's own baseline memory footprint (not connection count, as first suspected) via direct /proc RSS measurement. A memory increase plus a pinned buffer-pool size is deployed, but it's sitting in a 48–72h clean-run verification window before this gets called closed.
LowThe stocks-feed dashboard still shares one Y-axis across three tickers at very different price magnitudes — the same crowding issue already fixed on the crypto dashboard, not yet ported over.

What's next

Porting the crypto dashboard's per-symbol axis fix to the stocks feed, and closing out the DB memory verification window.
